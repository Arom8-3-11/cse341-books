5.b. How did you store sensitive data? Why is that approach important?

Answer:
I stored the MongoDB connection string in an environment variable,
MONGODB_URI. Locally, the development command loads it from my .env file.
On Render, it is configured in the service's environment settings. The
database connection code reads it through process.env instead of putting
the connection string directly in the source code. 

My .gitignore excludes the real .env file. The .env.example file contains
only placeholders and configuration examples, not my credentials. This
keeps sensitive connection information out of GitHub and lets me use
different configuration locally and on Render without changing the code.
this will also prevent the information from being leaked into any part of
the rest of the code.

6.b. What decision does this file show, and why did you make that choice?

Answer:
I used distinct 200, 404, and 500 responses. When testing an application,
it can be hard to figure out what is causing an issue. Different status
codes help distinguish a successful request from a missing book or an
unexpected server failure.

The single-book controller returns 200 with the book when it is found.
If the requested id does not match a book, it returns 404 with the JSON
message "Book not found". If an unexpected error occurs, it logs the
diagnostic on the server and returns 500 with "Internal server error".
These are JSON responses, not redirects to an error page. The generic
500 message avoids exposing internal database details to the client,
while the server log helps with debugging.
